# 時のオカリナ — 「ドアで場所を移動する」設計思想の抽出

2026-11-06。自作ゲームで「ドアに入って場所を遷移する」を作るときの参考。バグ解析とは無関係。
zeldaret/oot(decomp)の `z_door_warp1.c` / `z_en_door.c` / `z_player.c` / `z_play.c` / `z_demo.c` / `entrance_table.h` を読んだ範囲。
**コードで確認したこと**を主に書き、**そこから読み取った設計意図**は「意図」として分ける(意図は推測を含む)。

## 全体像: 移動は2階層

| 階層 | 単位 | 切り替えの重さ |
|---|---|---|
| シーン | ダンジョン1つ、フィールド1つ、など | 重い。`Play_Init` で全部作り直す |
| ルーム | シーン内の部屋 | 軽い。部屋のデータだけ入れ替える |

ドアは両方の役割を持つ。

- **部屋間のドア**: 同一シーン内。`transitionActors.list` の `sides[0]` と `sides[1]` に「手前の部屋」「奥の部屋」が書かれている。プレイヤーが近づくと、`z_player.c` が反対側の部屋を `Room_RequestNewRoom` で先読みする(5524行目付近)。シーンは切り替えない。
- **シーン出口ドア**(`DOOR_SCENEEXIT`): 別シーンへ行く。出口として、`exitList` に入った遷移先を使う。

## 設計思想1: 遷移先は「ドアが持つ」のでなく「データの表が持つ」

- ドアのアクタ(`En_Door`)は、行き先を知らない。持っているのは「どの種類のドアか」(通常、施錠、少し開いている、調べられる、シーン出口)だけ。
- 行き先は、シーン側の `exitList`(出口番号 → エントランス番号)と、グローバルな `gEntranceTable`(エントランス番号 → シーン、スポーン位置、演出)で決まる。
- ドアのアクタ、シーンのデータ、遷移先の表が、疎に結びついている。
- 意図: ドアを増やすのも、行き先を変えるのも、データ編集で済む。アクタのコードは変えなくていい。

## 設計思想2: 「ドアを開ける」の主導権はプレイヤー側にある

- `En_Door` は受け身。毎フレーム、プレイヤーとの相対位置と向き(距離と角度の範囲)を調べ、範囲内で操作されたら `player->doorType` などにドアの情報を渡す。
- 実際のドアを開ける動作(アニメ、カメラ、プレイヤーの状態フラグ)は `z_player.c` が持つ。プレイヤーの状態機械(`stateFlags1`)が「ドア操作中」に入る。
- ドアのアクタは `playerIsOpening` の旗が立ったら自分のアニメを再生する。
- 意図: 「いま何を操作中か」をプレイヤーの状態機械に集めておけば、ドア以外(梯子、段差など)も同じ型で扱える。ドア側は表示と当たり判定に専念できる。

## 設計思想3: ドアの種類は状態機械(`actionFunc`)の差し替え

- `EnDoor_Idle` → `EnDoor_Open` → ... のように、1つの関数ポインタ `actionFunc` を差し替えて状態遷移する。
- 施錠は `lockTimer` と、シーン内のスイッチフラグ(`Flags_SetSwitch`)で表す。鍵を使った記録はセーブされるフラグ側にあり、ドア本体の変数ではない。
- 意図: 見た目の状態(開閉)と、永続的な状態(鍵を開けたか)を分けている。シーンを入り直しても、フラグから復元できる。

## 設計思想4: 遷移は「予約して、演出が終わってから実行」

遷移の流れ(`z_play.c`):

1. 誰かが `play->nextEntranceIndex` に行き先を書き、`play->transitionTrigger = TRANS_TRIGGER_START` を立てる(予約)。
2. `Play_Update` が次のフレームで `transitionMode = TRANS_MODE_SETUP` に入り、フェードアウトを開始。
3. フェードが完了した時点で、はじめて `gSaveContext.save.entranceIndex = nextEntranceIndex` を実行し、次の `Play_Init` を予約して、現在のシーンを終了する。

- 意図: 「遷移したい」という要求と「実際に切り替わる」処理を分ける。間にフェード演出が入るので、重い読み込みを見せない。要求側はどのコードからでも同じ書き方で出せる。

## 設計思想5: 行き先の「別バージョン」を連番で並べる

- エントランスの表は、同じ場所の複数バージョン(時間帯、年齢、カットシーンの有無)を、連続した番号で並べている(例: 賢者の間は 0x06B〜0x071)。
- 引き方は `gEntranceTable[nextEntranceIndex + sceneLayer]`。`sceneLayer` は、現在のカットシーン番号などから決まるオフセット。
- 意図: 「どこへ行くか」と「どのバージョンへ行くか」を別々の変数で持ち、足し算で1つのエントリを決める。同じ出口データを使い回せる。

## 設計思想6: イベントも同じ遷移機構を使う

- ボス撃破の青ワープ(`z_door_warp1.c`)、カットシーンの終了(`z_demo.c` の `CS_DEST_*`)、穴や虚空への落下(`Player_HandleExitsAndVoids`)は、どれもドアと同じ変数に書く。
- つまり「ドアに入る」は特別な処理でなく、「遷移要求を出す」手段の1つに過ぎない。
- 意図: 場所の移動を出すコードが何であれ、受ける側(`Play_Update`)は1つ。

## 設計思想7: 遷移の演出も表のデータ

- 各エントランスに、フェード種別(黒、白、ゆっくり白、など)が2つ付いている(入る時と出る時の想定)。`z_play.c` 側で型を見て演出を切り替える。
- 意図: 演出もデータなので、場所ごとに変えられる。

## 自作に持ち込むときの論点(ここからは提案でなく整理)

OoT のやり方が持つ代償も、コードから読み取れる範囲で書く。

- **状態が複数の変数に分散している。** 行き先、バージョン、発火の旗が別々。誰が書いてもよいので、書き手が増えるほど「誰が最後に書いたか」の管理が必要になる。排他は `transitionTrigger == OFF` のチェックだけ。
- **予約が取り消され得る。** `z_demo.c` 247行目のように、遷移が先に始まると、予約されていたカットシーンが捨てられる。
- **データ駆動の代償として、番号が意味を持つ。** 連番の並び順そのものが仕様になっている。番号の追加・並べ替えは、参照する全データに影響する。
- **決めるべき分岐**: 2階層(シーン/ルーム)に分けるか、1階層にするか。ドアの主導権をプレイヤー側に置くか、ドア側に置くか。遷移を即時にするか、予約制にするか。
