# 引き継ぎ書: ローカル画像生成による素材・デジタル資産スタック

作成日: 2026-11-07 / 対象: CLIエージェント(Claude Code など)/ 依頼者: Kilphy

## 0. 目的

アプリで使う素材・デジタル資産(キャラクター、UI素材、表情違いのセットなど)を、**ローカルの画像生成AIで作って管理する仕組み**を作る。

- 指定した素材を作る(テキストから)。
- **1枚の基準画像から、表情・ポーズ違いを複数作る**(キャラクターの一貫性)。
- 作った素材を、メタデータ付きで資産として蓄積する。
- 動的な表情切り替えは、**事前生成して同梱し、実行時は選択・合成するだけ**にする(下記「設計方針」参照)。

## 1. 決定事項(変更する場合は依頼者に確認)

1. **ローカル優先**。クラウドAPIは費用が払えないため、補助(品質が足りない場合のみ・月額上限付き)に限る。
2. 実行環境は **Apple Silicon Mac(統合メモリ24GB)**。
3. Python環境は **uv**。単発の実験コマンドは `uvx`、同じツールを3回以上使ったら `uv init` を提案する。
4. ライブラリを試す場合は、シェルのワンライナーではなく、**数行の短いPythonファイル**を渡して編集・実行できる形にする。
5. 個人用の再利用可能な基盤を作る方針。マネージドSaaSへの依存は避ける。
6. **商用利用できるライセンスのモデルだけを使う**(次節)。

## 2. モデルの候補とライセンス(2026-11-07時点の調査)

| モデル | ライセンス | メモリ目安 | 用途 |
|---|---|---|---|
| FLUX.2 klein 4B | Apache 2.0 | 約13GB | 参照画像から表情違い(複数参照は4枚まで)。第一候補 |
| Z-Image Turbo | Apache 2.0 | fp8で約13GB | 素材の下絵・大量生成 |
| Qwen-Image-Edit(〜2511) | Apache 2.0 | 約54GBの記載あり | 24GBには重い。当面は対象外 |
| FLUX.2 dev / klein 9B | 非商用(商用は別途BFLライセンス) | – | **使わない** |
| Qwen-Image 2.0 / 2.0 Pro | – | – | API限定のためローカル不可 |

- Qwen-Image-Layered(レイヤー分解、Apache 2.0)は、パーツ単位の表情差分に使える可能性がある。メモリ要件は未確認。
- ライセンスは更新されるため、**モデルを導入する時点で、配布元(Hugging Faceなど)の最新ライセンスを確認する**。

## 3. 未確認事項(最初に検証すること)

- [ ] klein 4Bの**複数参照編集**が、Mac上のComfyUIまたはDraw Thingsで動くか、動くならどの程度安定するか。
- [ ] 24GB Macでの1枚あたりの実測時間(記事では「数秒〜数十秒」。RTX 4090の3〜5倍という目安もある)。
- [ ] Ollama(`x/flux2-klein`, `x/z-image-turbo`)は生成のみで、img2img・インペイント・LoRA・ControlNetには未対応。**表情違いの編集には使えない前提**で、ComfyUI / Draw Things / diffusers などを検討する。
- [ ] 透過PNGは、ローカルでは単色背景で生成して背景除去(`rembg` 等)する方針。品質を確認する。

## 4. 設計方針

```
素材リクエスト(YAML/JSON: 種類・参照ID・サイズ・背景)
        ↓
  provider層(既定: ローカル。差し替え可能にしておく)
        ↓
  後処理(背景除去 → リサイズ → スプライトシート化 → WebP化)
        ↓
  アセットストア(画像 + メタデータ)
```

- **provider層は薄く保つ**。モデルの入れ替わりが速いので、モデル名や接続先は設定で切り替えられるようにする。ローカルを既定に、クラウドは任意の追加providerとする。
- **メタデータを必ず保存する**: model / prompt / 参照画像ID / seed / 日時 / 後処理の履歴。再生成の根拠になり、法的にも「人間の関与」を説明する記録になる。
- **表情違いの作り方**:
  - 基準画像は、正面・無表情・単色背景で1枚決める。
  - 参照は2〜3枚(顔と、全身・衣装)にして、毎回同じ参照を付ける。
  - プロンプトには「変えるもの」と「変えないもの」の両方を書く。
  - チェーン編集は少しずつずれる(ドリフト)ので、毎回基準画像から作り直す。
- **動的な表情**: 生成には数秒〜数十秒かかるため、ユーザー操作のたびに生成しない。表情を8〜12種ほど事前生成して保存し、実行時は選択・切り替えだけにする。配布アプリでは、素材を同梱する。実行時生成が必要な機能がある場合のみ、上限付きの外部APIを検討する。

## 5. 法的な方針(実装への反映)

調査の要点(一般情報であり法的助言ではない):

- 日本(文化庁の整理): **人間の創作的寄与がなければ、AI生成物は著作物にならない**。簡単な指示だけの生成物は著作物に当たらないと考えられる。日本ではプロンプトに関する個別の判例はまだない。
- 米国著作権局: プロンプトだけでは著作者になれない。**人間が作った入力が出力に知覚できる部分、素材の創作的な選択・配置・修正は保護され得る**。複数案から選ぶだけでは創作と認められない。
- 保護を強める作り方: **自分で描いた原案を参照にする** / 手で加筆・修正する / 素材の選択・配列を創作的に行う(編集著作物、著作権法12条) / 制作過程を記録する。
- 編集著作物で保護されるのは、**セット全体の選択・配列の創作性**で、個々の素材ではない。編集方針や設計意図を文書として残す。
- 侵害の判断は、依拠性と類似性で行われる。生成物を公開した利用者が原則責任を負う。そのため、
  - 既存キャラクター名・実在人物名・ブランド名をプロンプトに入れない。
  - 他人のイラストや顔写真を、許可なく参照画像にしない。
  - 主要キャラやロゴは、公開前に逆画像検索で類似を確認する。
- **公開・商用リリース前に、弁護士または弁理士へ相談する**(初回相談で十分)。

## 6. 最初のタスク(順番に、各段階で依頼者に確認)

1. **M0: 実現性の検証**(Mac上で実行)
   - 基準画像1枚から、klein 4Bで表情違いを数枚作る。品質と所要時間を記録する。
   - まずOllamaで生成のみを確認し、次にComfyUIまたはDraw Thingsで参照編集を試す。
2. **M1: 最小パイプライン**: リクエスト(YAML) → 生成 → 保存(メタデータ付き)。
3. **M2: 表情セット**: 基準画像 → 8〜12表情 → 一貫性の確認。
4. **M3: 後処理**: 背景除去・リサイズ・WebP化。
5. **M4: マニフェストとスプライトシート**: アプリが読める形で書き出す。
6. **M5(任意)**: 上限付きのクラウドprovider(月の予算上限を設定)。

## 7. クラウドを補助に使う場合の参考価格(2026年11月ごろの調査。必ず公式で再確認)

- FLUX.2 klein 4B API: 1枚あたり約$0.014から(公式)。
- GPT Image 2(1024×1024): low / medium / highで約$0.006 / $0.053 / $0.211。
- Nano Banana 2(Gemini API): 1Kで約$0.067。バッチなら半額の階層がある。
- OpenAIは、APIの出力に関する知的財産侵害の補償を提供している(除外条件あり)。
- 費用の上限を超えない仕組み(月の上限、キャッシュ)を最初から入れる。
